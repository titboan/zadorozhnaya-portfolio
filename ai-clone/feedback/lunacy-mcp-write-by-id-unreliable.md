`update_layers` вернул `"Updated 36 layers successfully"`, и `get_layers_by_ids` сразу после подтвердил новые имена — но это оказалось эхо/кэш вызова, а не реальное состояние документа. После того как Боря просто сохранил файл (`Ctrl+S`, без перезагрузки), повторный `get_layers_by_ids` на том же ID показал СТАРОЕ имя. В `get_undo_stack` запись про переименование пропала вообще — вместо неё была только реальная операция Бори (Lock слоя).

**Why:** Официальный API_REFERENCE Lunacy plugins (github.com/icons8/lunacy-plugins) утверждает, что `/updatelayers` «Creates single undo operation for all updates» — то есть по документации это должно было сработать. По факту — нет. Официально задокументированная и явно оттестированная icons8 фича — конкретно «LLM can edit Selection over MCP» (релиз 11.6, отдельно от более новых «additional methods» из релиза 12, куда попали update/create/delete/duplicate by ID). Похоже, что путь через `set_selected` (редактирование текущего выделения) — единственный по-настоящему проверенный производителем механизм записи; методы по произвольным ID — более новая, менее обкатанная надстройка, и в этой версии (Lunacy 14.1.0.0) она не пишет в реальный документ, хотя API отвечает успехом.

Не путать с чтением — `get_layers_by_ids`, `get_layers_in_area`, `export`, `get_selected` по произвольным ID читают корректно (это подтверждено множеством успешных экспортов картинок в этой же сессии). Проблема именно в WRITE-операциях по ID.

**How to apply:**
- Не доверять успешному ответу `update_layers`/`create_layers`/`delete_layers`/`duplicate_layers` как доказательству, что изменение реально в документе
- Единственная проверка, которой можно верить — попросить пользователя посмотреть глазами на живую панель в Lunacy (не через API get_layers_by_ids сразу после записи — она может echo-ить то же кэшированное состояние)
- Если нужно реально что-то поменять (переименовать/сгруппировать/удалить) — просить Борю выделить это в живом приложении, читать через `get_selected`, слать изменённую копию через `set_selected` (это и есть официально протестированный «edit Selection over MCP», релиз 11.6)
- Для проверки, что MCP-связь вообще жива (в отличие от того, дошло ли конкретное изменение) — `show_toast` даёт однозначный визуальный сигнал пользователю
- См. также `figma-passthrough-blend-mode.md`, `lunacy-figma-import-clipboard-silent-fail.md` — тот же паттерн «Lunacy делает не совсем то, что документировано/ожидается» для .fig-импорта

**Подтверждено 2026-07-21 (реальный тест с проверкой глазами пользователя, не только через API):**
- `set_selected` над текущим выделением (Боря выделил один фрейм «logo») — переименование реально применилось, Боря подтвердил визуально в панели, `undo` тоже сработал и вернул старое имя. Это рабочий и надёжный путь
- Формат вызова: `objectsJson` — **обязательно JSON-массив** `[{...}]`, даже для одного объекта (без обёртки в массив — ошибка `DeserializeUnableToConvertValue`)
- Инструмент сам проверяет ID против реального текущего выделения и явно говорит, если не совпадает («Layer ID mismatch... Current selection IDs: [...]») — это надёжный сигнал живого состояния, в отличие от `update_layers`
- На больших объектах (сотни вложенных векторных path) риск не в самом механизме, а в ручной передаче JSON через вызов инструмента — при печати вручную объёма ~40КБ+ была ошибка парсинга (`ZeroDepthAtEnd`, разрыв где-то в структуре при транскрипции). Для больших фреймов надёжнее строить/передавать через файл и Read, а не пытаться воспроизвести текст напрямую в параметре большого размера
- Практическое ограничение: `set_selected` требует, чтобы Боря заранее выделил именно то, что меняем — для десятков объектов по одному это дорого. Если объекты можно выделить одновременно (shift-click/marquee) — `get_selected` вернёт массив, и можно переименовать все разом одним вызовом `set_selected`
